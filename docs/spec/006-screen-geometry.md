# 006：畫面尺寸

狀態：`CONFORMED`

原版的顯示畫面是 **640×408**，不是 640×350。

這一份定案畫面高度，並記下四條各自獨立的一手證據。先前整個專案（remake
的畫布、對拍的取樣尺寸、DOSBox-X 的截圖、每一張基準畫面）一路用 350，
而那個數字沒有任何一條 `L0` 證據撐著。

## 1. 結論

| 項目 | 值 | 等級 | 版本 |
|---|---|---|---|
| 畫面寬 | 640 | `L0` | `[both]` |
| 畫面高 | **408** | `L0` | `[both]` |
| 每列位元組（EGA 平面） | 80 | `L0` | `[both]` |
| 一個平面用掉 | 32,640 B | `L0` | `[both]` |

`assets.ScreenW`／`ScreenH` 是唯一的一份；對拍那邊的 `scrW`／`scrH`
直接引用它，不再各記一份。

## 2. 證據

### 2.1 原版寫進 CRTC 的值（`L0`）

原版一次都沒呼叫 `int 10h AH=00`——BDA 的模式位元組一路停在開機值
`03h`，所以**沒有任何一格暫存器說過 350**。模式是直接寫暫存器換的，
答案在 CRTC（埠 `3D4`／`3D5`）。

dosgolem 不模擬 CRTC 的效果，但每一次埠寫入都記著
（`oracle.PortWrites`）。跑到主選單時原版設過的是：

| 索引 | 值 | 意義 |
|---|---|---|
| `06` | `A6` | Vertical Total（低八位）|
| `10` | `98` | Vertical Retrace Start |
| `11` | `25` | Vertical Retrace End |
| **`12`** | **`97`** | **Vertical Display End（低八位）** |
| `15` | `99` | Vertical Blank Start |
| `16` | `A4` | Vertical Blank End |

Vertical Display End ＝ 顯示列數 − 1。`97h` ＝ 151，配 Overflow
（索引 `07`）的第 8 位 ＝ **407**，也就是顯示 **408** 列。Retrace 與
Blank 的起點（`98h`、`99h` ＋ 第 8 位 ＝ 408、409）緊接在顯示結束之後，
與這個讀法自洽。

### 2.2 DOSBox-X 截出來就是 640×408（`L0`）

DOSBox-X 是完整的 VGA 實作，自己解讀 CRTC。`tools/dosboxx.sh` 抓到的
原始視窗**就是 640×408**（`workplace/shots/dosboxx/menu-raw.png`）。

這一份先前存在儲存庫裡，只是沒有人問它為什麼是 408。

### 2.3 原版自己的版面算術（`L0`）

主畫面的七張底圖，座標讀自 `0x11ebc`–`0x11fc5`：

```
MAINMAP1  (  0,   0)   640×36    上方花邊
MAINMAP3  (  0,  36)    72×336   左側直條
MAINMAP4  ( 72,  36)   168×336   地圖左半
MAINMAP5  (240,  36)   168×336   地圖右半
MAINMAPB  (408,  36)   224×153   右上面板
MAINMAPC  (408, 189)   224×184   右下面板
MAINMAP7  (632,  36)     8×336   最右直條
MAINMAP2  (  0, 372)   640×36    下方花邊
```

36 ＋ 336 ＋ 36 ＝ **408**，一列不多一列不少。主戰場同形：`0x2246a`
載 `MAINMAP1` 畫在 (0,0)、載 `MAINMAP8`（也是 640×36）畫在 (0,372)。

### 2.4 主戰場的底紋迴圈（`L0`）

`0x223e4` 的雙重迴圈把 `8x8PAT0.IMG` **鋪到 640×408**。這一條先前就
寫在 `internal/assets/battlescreen.go` 的註解裡，離「畫面只有 350 高」
四行。

### 2.5 dosgolem 的 VRAM（`L1`）

把畫面照 640×480 取出來逐列數非零像素
（`internal/parity/videomode_oracle_test.go`）：

| 畫面 | 0–349 | 350–399 | 400–407 | 408 起 |
|---|---|---|---|---|
| 開場三英圖 | 196,968 | 29,679 | **0** | 每列 640（另一份資料）|
| 主選單 | 180,332 | 25,940 | 有背景色 | 每列 640（另一份資料）|

三英圖那一列的形狀最清楚：`TITL0`–`TITL3` 四塊各 160×400，並排正好
640×400，貼滿 0–399；400–407 是原版貼圖前清成的黑；408 起是離屏資料。
**400 ＋ 8 ＝ 408。**

### 2.5 Hercules 那一側也是 640×408（`L1`、`[base]`）

裝置選單答 Hercules 時原版寫進 6845 的是 R1＝`0x28`（40 個字 ＝ 80 bytes ＝
640 px）、R6＝`0x66`（102 個字列）、R9＝3（每字列 4 條掃描線），102 × 4 ＝
**408**。與 EGA 那一側的 CRTC 值指向同一個高度，是第五條獨立證據
（`docs/re/00` 第四輪末段，`TestZZHerculesBootDrawsB0000`）。

## 3. 350 是怎麼進來的

`tools/dosboxx.sh` 曾有一句註解：

> 視窗是 640×408（上下各一條黑邊），畫面本體在左上角 640×350。

那句話自己就矛盾——上下都有黑邊的話不會從左上角裁。而下游的每一個
實作與每一張基準畫面都照著它做：remake 的畫布、對拍取樣的 `scrH`、
DOSBox-X 的 `-crop 640x350+0+0`、dosgolem 存的每一張 PNG。

於是「dosgolem 與 DOSBox-X 兩個獨立實作逐點相同」照樣成立——**兩條
路徑拿的是同一個錯前提**。`CLAUDE.md` §7 第 19 條要的「兩條路徑對同一份
資料逐格相同」，在前提本身沒被質疑時擋不住這一類錯誤。

前提要自己有證據，不能靠下游的一致性反推。

## 4. 這件事蓋掉了什麼

被 350 截掉的 58 列，在原版畫面上是有內容的：

| 畫面 | 350 以下有什麼 |
|---|---|
| 主選單 | 第三列按鈕（`3. 使用楷書字`／`6. 回作業系統`）的下半、左側直牌「主選擇單」的最後一個字、右下角小飾框的下半 |
| 主畫面 | `MAINMAP2` 整條下方花邊（372–408），以及右下面板超出 350 的那一段 |
| 主戰場 | `MAINMAP8` 整條下方花邊、三個面板下緣（268＋96 ＝ 364）、肖像 64×80 在 (72,276) 的下緣 356 |
| 開場三英圖 | 素材第 350–399 列 |

先前記在程式碼註解與 `docs/spec/005` 裡的「落在畫面外」「下緣被畫面
切掉」「只看得到上半」，全部是畫布設成 350 的結果，不是原版的行為。
