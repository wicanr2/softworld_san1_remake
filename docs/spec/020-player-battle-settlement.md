## 1. 收尾順序（`L0`、`[both]`）

四個軍團整編時都在 `0x20ce0` 將出征者人物 offset 19 清成 0，
再以 `0x1d638` 重整各來源郡；戰場郡在戰役期間可暫為無主。
因此決定「是否有玩家參戰」須使用整編前保存的四郡勢力，
不得在清空人物後才讀當下州郡所屬。

`0x23d03` 呼叫 `0x25652`，勝方援軍在勝方主軍仍有人的情況下回來源郡；
`0x23d08` 呼叫 `0x258f2`，敗方主軍及援軍逐隊強制退卻，退不了的人交
`0x259fe` 處置；`0x23d0c` 呼叫 `0x266a6` 安置勝方與戰場郡；
`0x23d17` 呼叫 `0x26c08` 處理退場君主、繼承與寶物。玩家正常路徑
`TestBattleFinishesWithPlayer` 已命中 `0x25652`、`0x266a6`、`0x26c08`
各一次（`L1`）。

## 2. 戰場郡與勝方（`L0`＋`L1`、`[both]`）

`0x266a6` 將敗方援軍、主攻軍、主守軍剩餘的隨軍金米加總，各夾到
30000，寫回戰場郡；勝方援軍已在 `0x25652` 把隨軍金米帶回來源郡。
四個受損欄位各擲一次：民忠 `max(0, 原值−RND(15)−3)`、土地
`max(0, 原值−RND(15)−2)`、洪水 `min(100, 原值+RND(10)+4)`、
物價 `min(70, 原值+RND(25)+5)`。這不是電腦對電腦的四個公式。

勝方主軍仍有人就由主軍駐戰場；否則由勝方援軍駐戰場。各生還將領的
人物 offset 19 寫戰場郡，軍團統帥寫州郡 offset 32；統帥若為一般武將
升太守，再 `RefreshGarrison` 戰場郡與相鄰郡。沒有「挑魅力最高的
攻方武將當太守」分支，也沒有「守方全員改當地在野」分支。

原版正常玩家戰役固定盤面一次命中：戰場郡 25 的金 0→5000、米
0→11892、民忠 100→96、土地 100→92、洪水 0→4、物價 44→70、
所屬 255→8。這是**該盤面的結果**，不是通用常數。
加強版 `0x23e70` 同樣加總三支軍團的金米，四擲是
`RND(15)`、`RND(15)`、`RND(10)`、`RND(25)`；
`0x24069` 寫勝方人物 offset 19，`0x240df` 寫主事者，
`0x24141`／`0x2416f` 重整戰場及相鄰郡。因此這一段無需版本旗標。

## 3. 退場君主的寶物（`L0`＋`L1`、`[both]`）

`0x26c08` 先檢查退場君主旗標 `es:20f0`，`0xffff` 就返回；否則呼叫
`0x14968` 處理繼承。然後只處理諸侯記錄 offset 15–18 的兵書、寶刀、
美女、駿馬：`RND(4)` 挑一類在敗方加 2；每類分給勝方
`half + RND(half)`，`half = 敗方件數 ÷ 2`，勝方上限 100。offset 14
的玉璽不在這支常式的讀寫範圍。加強版玩家戰後日循環在
`0x217ed` 呼叫對應的 `0x24338`；四類分贓算法已在
`docs/mechanics/90` §6 逐項核對，無需加版本旗標。

正向對照 `TestBattleFinishesWithPlayer`：原版正常玩家戰役的退場旗標
確實為 14，`0x26c08`、分贓第一擲 `0x26c31` 與返回後
`0x23d1d` 各有命中。於分贓擲骰前放入敗方 `[1,10,9,8,7]`、
勝方 `[2,1,1,1,1]`，返回後四類總量由 38 變 40、勝方玉璽
仍為 2。這個注入點在 `0x14968` 繼承**之後**，避免把繼承對玉璽
的處置誤算成分贓。

只有**實際令君主退場**的戰死、斬首或無處可去的釋放，才設定該旗標；
只捉到一般武將、或君主被釋放回有去處的郡，不觸發這一段。

## 4. 敗軍與先前退兵（`L0`、`[both]`）

日循環呼叫 `0x258f2`（加強版 `0x2320a`），迴圈依序處理敗方主軍與
援軍的五支部隊，以第三參數 `0xffff` 呼叫既有退兵常式 `0x23dd4`
（加強版 `0x21894`）。`0xffff` 令玩家選單不能空 Enter 取消；
退兵失敗就由隊伍後槽往前逐位交勝方軍力的 `0x259fe`（加強版
`0x23306`）處置。這不是電腦對電腦的 `0x1fb26` 逃散判定。

`0x23dd4` 成功時在 `0x242fb` 呼叫 `0x24318`：`0x245d0`
把生還者人物 offset 19 寫成所選郡；若所選郡無主，`0x245f5`
設所屬與主事者。remake 的 `Unit.RetreatTo` 應在戰後寫回所有已退兵
單位的生還者，不限於敗方；強制退兵的失敗者則走 `Battle.Capture`
既有處置。

## 5. 完成條件與限制

`READY`（`L0`、`[base]`）：玉璽「已現世」是獨立於寶庫的旗標。
春季事件在 `es:0x2f6c` 從 `0xffff` 寫為 0；無繼承人時
`0x14bcf` 只清勢力寶庫 offset 14，不重設該旗標。因此玩家戰役令
持玉璽的勢力絕嗣後，不得從各勢力寶庫反推「尚未現世」而再次觸發
春季事件。原版存檔 `BASEPRO` offset `0xc4` 已保存此旗標；
remake 的補充狀態與存讀檔須保留它。舊版補充存檔若沒有獨立旗標，
以當時寶庫為相容推斷；原版 `BASEPRO` 存在時以原版旗標為準。

- `L1`、`[both]`：`TestZZPlayerSettlementTables` 與
  `TestZZPlayerSettlementTablesPlus` 各從正常玩家戰役出發，在原版結算
  入口擷取三張表、四軍狀態與當時的 MSC 亂數狀態，讓 remake 從同一份
  位元組與種子接續。入口三表逐位元組相同；結算返回後，兩版各自的
  **整張州郡表 7,568 B 與人物表 10,500 B 都是 0 差**。原版固定
  戰役起始 seed 是 `0x13579bdf`；結算入口 seed 原版
  `0x46f1f4fc`、加強版 `0x8cefa24f`。原版入口／返回三表 SHA-256
  分別為 `4919cd2972f78ed5a885b066d1edbf4e70abcaba393d150ccfdc9c1ea53bc151`／
  `599d4be7340ea49ecdfedb54c69f3c36e7537a214fb9ce6ce17a0b608d96b7cd`；
  加強版為 `82efca6df4c97a62c53b4b875c10ef20021c54ab452aeed747653890ef65bc78`／
  `0ba234162a928c904d6398b179894f8ad982329e4720c050e557b638137824a0`。
  收據由 `SAN1_TIMEOUT=25m tools/go.sh test ./internal/parity -tags oracle -count=1 -run '^TestZZPlayerSettlementTables(Plus)?$' -v`
  重生，兩支測試通過。
- 此切點只隔離**戰後結算**：原版戰術層的結果交給兩側共用，並未證明
  remake 從整編、逐日按鍵到結算的完整路徑逐步相同。諸侯表也未列入
  此閘門：原版在入口前已更新人望、退場君主已從部隊名單移除；重播
  `settle` 會再做一次人望，且不能從存活部隊重建先前的君主死亡事件。
  因此戰後諸侯表原版／加強版仍差 12／2 B，保留為明示的對拍切點限制，
  不將整份規格升為 `CONFORMED`。
