# 015：原版 oracle 的行為觸發開機

狀態：`CONFORMED`（2026-09-13；六項原版整組驗收全數通過，無跳過。2026-09-15 加 §8 加強版與開新遊戲）

範圍：`base` 版原版從 `AA.EXE` 開始，走「載入舊進度第 1 格」到第一個
遊戲主命令輸入；以及執行「內政 → 休息 → 確認」後，到下一次遊戲主命令
輸入。這是測試驅動契約，不改 remake 的玩家規則或存檔格式。

排除範圍：其他存檔槽、原版逐指令時序，以及硬體鍵盤 IRQ1 的逐週期
一致性。加強版與開新遊戲在 §8（2026-09-15 補，Issue #20）。

## 1. 輸入與工具

| 項目 | 值 |
|---|---|
| 原版輸入 | `org_game/三國演義/AA.EXE` |
| SHA-256 | `474780e5be697b3b4899da5e0dbadd2f327e0bbe7e56306ac3b732a15fc124ca` |
| dosgolem-san | `d351681ba86d97aab571d00b979c36e2336486f3` |
| IDA | IDA Pro 9.4，`ida-pro-9.4-idapython:locked-v1` |
| 執行期碼段樣本 | runtime `1058:0000` 起 64 KiB，SHA-256 `bdd909257763393c2d4fe17a21ba451c425d9068dad98ceabf878e516e6bb232` |

IDA 的 `AA.EXE.i64` 靜態位址空間與這個自解壓後的執行期碼段**不可直接
互換**。本規格的 `1058:xxxx` 一律是 dosgolem 執行期 `CS:IP`；IDA 只把
上述 64 KiB 原始碼段以檔案 offset 0 ＝ runtime `1058:0000` 載入作交叉
驗證。不得把正式資料庫的同數值位址拿來替代。

## 2. 輸入底層（`L0`，`base`）

runtime `1058:0E24` 是掃描碼輸入常式入口。保留原位址與 bytes：

| 原始定位 | bytes／控制流 | 附加語意 | 等級 |
|---|---|---|---|
| `1058:0E24` | `33 C0`；其後 far call `05C4:051C` | 初始化一次按鍵讀取 | 已證實 `L0` |
| `1058:0E45` | `or ax,ax`；`1058:0E47 jnz 0E2E` | 等上一鍵放開 | 已證實 `L0` |
| `1058:0E57` | 呼叫同一底層常式，參數 1 | 等新鍵按下；正式送掃描碼的同步點 | 已證實 `L0` |
| `1058:0E63` | `or ax,ax`；`1058:0E65 jz 0E4C` | 沒有新鍵就繼續等待 | 已證實 `L0` |
| `1058:0E7F` | 返回 `AL` | 回傳讀到的鍵 | 已證實 `L0` |

先前曾把 `1058:065F` 當成輸入等待點；執行期 bytes 證明它其實是
`call dword ptr es:[bx+2176h]` 的十六項分派器。該假說作廢，保留在研究
歷程中，不得再作同步點。

## 4. `READY` 輸入狀態機

1. 依三次 `KeyWaits` 分別用 DOS 字元路徑送 `1`、`2`、`2`。
2. 等故事畫面 `c805…`，只走字元路徑送 Enter；不可用 `TypeBoth` 留下
   此時尚無 IRQ1 消費者的硬體掃描碼。
3. 等標題畫面 `8dc9…`，再等 BIOS wrapper `0583:3792` 由 caller
   `0AD0:0104` 以參數 1 輪詢新鍵，透過 BIOS 佇列送 `Return`。
4. 等 `MENU3.IMG` 與 `1058:15F7`；在 `1058:0E57` 送掃描碼 `2`。
5. 等 `1058:3C9B` 與存檔槽畫面；在 `1058:0E57` 送掃描碼 `1`。
6. 等 0..9999 輸入及密碼畫面；在 `1058:0E57` 送 `1`＋Enter。
7. 等 `03EB:02DE`，送 `Y`。
8. 等 `1538:2EB8` 與玩家選擇畫面；在 `1058:0E57` 送 `1`＋Enter。
9. `1538:236B` 出現即為 `bootToMain` 成功停點。
10. 要前進一個玩家回合時，在每次 `1058:0E57` 分別送 `4`＋Enter、
   `4`＋Enter；等 `1538:528C` 送 `Y`；下一次 `1538:236B` 即為
   `bootToGame` 成功停點。

所有 `Budget` 只是失敗即關閉的上限。跑滿上限必須報錯，不能當成功停點，
也不能依實測步數排程送鍵。

## 5. 影響、失敗模式與驗收

- 玩家垂直路徑：原版執行檔 → 裝置題 → 開場 → 主選單 → 載入進度 →
  畫面所示密碼／確認 → 玩家選擇 → 主命令；不走 direct-entry。
- 存檔影響：無；只讀原版第 1 格並讀取執行期三張表。
- 失敗模式：錯誤輸入路徑留下殘鍵、畫面指紋不符、caller 未出現、掃描碼
  同步點未出現、輸入範圍不符，全部失敗即關閉。
- 內部驗收：`turn_oracle_test.go` 與 `screenshot_oracle_test.go` 的開機步驟
  不得用固定 `o.Run(數字)` 作觸發。
- 原版驗收：行為觸發的 `bootToMain`、`bootToGame` 能由乾淨原版重生；固定
  seed 的月度同狀態對拍在新起點差 0 個位元組，且沒有跳過測試。
- 已知差異：執行預算仍以指令數表達，但只作逾時護欄；這不是原版逐週期
  parity，也不影響成功狀態。
- 停止線：不深挖 IRQ1、PIT 或鍵盤硬體逐週期，只保留足以同步玩家可見
  流程的 `L0`／`L1` 證據。
- 權利邊界：原版執行檔、畫面與執行期碼段只留本機，不加入 Git 或公開包；
  版控只保存雜湊、位址、短 bytes、狀態機與測試程式。

## 6. 實作回饋（2026-09-13，`DRAFT` → `READY`）

較早的行為觸發開機探針曾停在月游標 22；但固定 seed
`0x13579BDF` 的 38 郡月度視窗仍差 4 bytes：人物 188、336 的訓練與武裝
各多 1。進一步沿原版編隊清單查明：這兩郡各只有一支部隊，原版仍執行
`0xc2c4` 的百分比重算，remake 卻以清單少於兩支跳過。AI 單支路徑補回後，
同一 seed、同一 38 郡視窗重跑差 0 bytes；玩家命令仍維持至少兩支。

先前輸出中原版／remake 亂數總數為 2082／2081，且「駿馬」分桶顯示
33 次歸戶差異；但十張分派表合併後的抽樣數逐表相同，修正也不涉及賞賜。
因此那兩個數字只作時間窗／診斷分桶限制，不再當成 4-byte 差異的原因。
後續補齊故事畫面與標題畫面的兩段輸入路徑後，正式成功停點改為月游標 17；
游標 22 與上述 4-byte 缺口保留為錯誤起點如何暴露問題的歷史，不再代表現行
對拍起點。

## 7. 標題 BIOS 輸入證據與最終收據

runtime `0583:3792` 的原始 bytes 以 `55 8B EC 8A 66 06 8A D4 80 E2 0F
CD 16 …` 開始：從參數取 BIOS 功能號、遮成低 4 bits 後呼叫 `int 16h`。
`0AD0:00D4–00F9` 先以 `AH=01` 查鍵、`AH=00` 讀掉既有鍵；
`0AD0:00FB–0113` 再以 `AH=01` 等新鍵，caller `0AD0:0104` 即正式
同步點。以上位址全是 dosgolem runtime `CS:IP`，推論等級為已證實 `L0`；
不等同 `AA.EXE.i64` 靜態位址。

2026-09-13 以 `SAN1_SEED=0x13579BDF`、原版第 1 格、同一乾淨容器執行：

- `TestBehaviorTriggeredBootReachesNextMainCommand`：通過，停在月游標 17。
- `TestOriginalSaveLoadsIdentically`：通過，三張表 19,220 bytes。
- `TestZZMonthParity`：通過，38 郡視窗差 0 bytes。
- `TestPasswordAnswerDoesNotMatter`：通過，兩答案低記憶體差 4 bytes／2 段，
  在既有 64-byte 輸入緩衝門檻內。
- `TestZZOriginalLoadedScreen`、`TestZZOriginalOpeningScreens`：通過。
- 整組結果：6 PASS、0 FAIL、0 SKIP，套件耗時 253.644 秒。

## 8. 加強版與開新遊戲（`L1`、`[both]`；Issue #20）

### 8.1 加強版的路標（只對 `ASV.EXE` SHA-256 `ad18a251…` 成立）

加強版用 286 指令編譯（`push imm8`、`imul r,m,imm8`），主程式那一層的
呼叫端形狀與原版不同，選單三步用畫面雜湊等；runtime 那一層形狀對得上，
掃描碼等待點是拿原版 `1058:0E24` 的指令序列比出來的。位址全是線性。

| 路標 | 原版 | 加強版 | 怎麼定的 |
|---|---|---|---|
| 掃描碼輸入常式 | `1058:0E24`（`0x113a4`）| `0x10b8e`（`0FE4:0D4E`）| 形狀：`xor ax,ax / call 05B9:051E / … / push 0x63 / call 分派器` |
| **等新鍵**（送掃描碼的同步點）| `1058:0E57`（`0x113d7`）| **`0x10bbd`**（`push 1 / call 05B9:378E`）| 同上，`waitPlusScan` |
| 十六項分派器 | `1058:065F` | `0x1043e`（`es:[bx+0x2178]`）| 形狀 |
| 數字輸入常式 | `33D8:115E` | `0x317e4` | 形狀（`docs/re/11` §2 的方法）|
| Y/N 輸入常式 | `0x1538c` | `0x144ba` | 形狀 |
| 選君主（1..6）呼叫端 | `1538:2EB8` | `0x11848` | 實跑攔到 |
| 難度呼叫端 | `0x122ff`（1..10）| `0x1192e`（1..20）| 實跑攔到 |
| 密碼（0..9999）呼叫端 | `03EB:02C2` | `0x4100` | 實跑攔到 |

每一張表的六個等級各是一個遠指標（8 格 × 4 byte），指到的常式位址
在 `plusDispatchTables` 那一輪對拍時從 DGROUP dump 讀出來；逐表的差異
在 `docs/mechanics/90` §6.5。

### 8.5 加強版玩家命令對拍的路標（`L1`、`[plus]`；Issue #27）

`TestPlayerCommandsPlus` 與原版那支共用同一張命令表與同一支本體
（`runPlayerCommandsRig`），差的只有 `playerRig`：

| 路標 | 原版 | 加強版 |
|---|---|---|
| 目前的郡 | 工作段 `+0x30fc`（`o.ES()`）| 工作段 `+0x3106`（段從 `DS:[0xa8f8]` 取）|
| 守將清單／筆數 | `DS:[0xa668]` 段 `+0x58c`／`DS:[0xa666]` 段 `+0xc` | 工作段 `+0x5a0`／`+0xc` |
| 月迴圈每一格那一抽（玩家回合結束的訊號）| `0x15790` | `0x147f0`（`push 0xc / call RND`）|
| 回合結束重整守將清單 | 沒有 | `0x162e0`（`docs/mechanics/90` §6.6）|

**兩個帳要分開**：開新局那個月電腦的郡已經跑過一輪，逐郡、逐表的計數
要從月底結算那一刻歸零，否則每一張表都會算成兩個月的量（看起來像
「加強版每張表都跑兩次」）。逐表的抽樣次數用**種子法**——記每一張表
呼叫端那一刻的種子，兩張表之間走了幾步 LCG 就是前一張抽了幾次，
`RND(0)` 這種不抽的呼叫自然不算；月迴圈每一格的那一抽（原版 `0x15790`
的對應）落在出兵與下一個入口之間，算本體時扣掉。
