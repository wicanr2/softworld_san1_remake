## 2. S04 提供的資料表版面（最有價值的一項）

S04 的「修改」段落指出修改目標檔案是 **`DATA2.GRP`**，並用「磁區#位置」
（sector#offset）標出各段資料的起點。這種標法通常代表原作者當年是用磁碟編輯器
（以 512 byte 磁區為單位）在操作。

**但這些位址很可能就是 `DATA2.GRP` 的檔案偏移量。** 換算後最大的一個位址是
存檔六的人物資料 `2031#501` = 1,040,373，加上該區塊長度後約 1,051,515；
而專案內 `DATA2.GRP` 的大小是 **1,156,221 byte**——全部落在檔案範圍內，
而且只剩約 10 萬 byte 餘裕。若基準點另有偏移，這種吻合不太可能發生。

**這是本文件的推論，動手前先在真實檔案上驗一次。** 驗法很便宜：
跳到 offset 818,235（劇本一的州郡資料）讀 5 byte，看是不是一個兩字 Big5 郡名加 NULL。

### 2.3 這兩張位址表自己驗證了自己

把「磁區」當成 512 byte、換算成線性位址之後，十二個區塊的內部結構完全一致：

| 量 | 值 | 說明 |
|---|---|---|
| 諸侯區長度 | **1326** byte | 十二個區塊全部相同 |
| 州郡區長度 | **7392** byte | 十二個區塊全部相同，且 **7392 = 42 × 176**，與 S04 宣稱的「42 郡、每郡 176 byte」**完全吻合** |
| 劇本區塊間距 | **19220** byte | 六個時期等距 |
| 存檔區塊間距 | **19860** byte | 六個存檔槽等距 |

`7392 = 42 × 176` 這個等式是本次研究最紮實的一項結果：它同時驗證了三件事——
「磁區」確實是 512 byte、郡數確實是 42、郡結構確實是 176 byte。
三個獨立敘述在一條算式上對上，不太可能是巧合。

各區塊的組成：

```
劇本區塊 19220 = 諸侯區 1326 + 州郡區 7392 + 人物區 10502
存檔區塊 19860 = 諸侯區 1326 + 州郡區 7392 + 人物區 11142
```

### 2.4 兩個對不上的地方（開放問題）

**諸侯區 1326 byte 不是 72 的倍數。** `1326 ÷ 72 = 18.42`。兩種可能：

- 諸侯記錄實際是 **78 byte**（`1326 = 78 × 17`，剛好 17 筆），S04 的「72」記錯；
- 或記錄確實是 72 byte、共 18 筆（1296 byte），後面接 30 byte 的其他東西
  （30 剛好等於一筆人物記錄的長度，可能是巧合）。

S04 列出的六個時期，可選君主槽位最多是 16 個（時期一、二）。17 或 18 都比 16 大，
所以兩種解釋都不會與君主表衝突。**待驗，用位元組解決。**

**人物區在劇本與存檔中長度不同**（10502 vs 11142，差 640 byte）。
若人物記錄是 30 byte，`10502 = 30 × 350 + 2`、`11142 = 30 × 371 + 12`，
兩邊的餘數不一致，表示至少有一個假設不成立：可能是人物記錄不是 30 byte
（S04 自己的欄位累加也只有 29，見 2.7 節），也可能區塊之間有不等長的填充，
也可能存檔多存了一段劇本沒有的執行期狀態。

> 上面的換算是本文件依 S04 的數字推算的，不是 S04 原文。
> 「磁區 = 512 byte」這個前提已由 `7392 = 42 × 176` 反過來佐證，
> 但仍應在真實檔案上再確認一次。

這張表的資訊密度最高，幾個直接可用的結論：

- **等級**與**職業**是兩個獨立欄位。等級決定帶兵上限（君主 5000 …牙將 1500），
  職業決定當下的任務身分（君主／軍師／太守／部將／在野）。
- `職業 = 0B（等待尋找）` 印證了「尋訪人才」指令的機制：未登場的人才在資料檔中
  一直存在，只是狀態為「等待尋找」。
- `職業 = 0C（死亡）` 表示死亡是狀態旗標，武將條目不會被移除。
- **兵種是位元組合**：`03=山陸`、`04=水陸`、`05=山水`——但 3/4/5 的編號不是
  `bit0=山 | bit1=水 | bit2=陸` 那種乾淨的位元遮罩（那樣 山陸 應該是 0|4=…）。
  看起來只是七個列舉值。**待驗。**
- **姓名 6 byte = 3 個 Big5 字**。這對 remake 的姓名處理是硬約束：
  四字姓名（如「司馬懿」是三字，但「諸葛亮」也是三字）都塞得下，
  但如果存在四字人名就會有問題。S04 的武將表中最長也是三字。
- **死亡年齡**是預先寫死在資料中的欄位，而非執行期隨機——這解釋了 S04
  「最後死亡的依次為曹髦、文虎、文鴦」這種可以事先知道的斷言。

## 3. 保護機制與破解（S04）

S04 記錄的破解位元組（`--` 表示該位置不動）：

```
ASV.EXE（用 UNP 解壓二次）
  FE C9 94 8D A5   (二次)
  -- DE -- -- --
  86 AE 4A B0 B3   (二次)
  -- A4 -- -- --

加強版破解碼：
DATA5.GRP（先填回記號 20 20 20 20 -> 4C 5A 39 31 再解壓）
  80 3F 00 74 04
  -- -- -- 90 90
```

### 3.1 `4C 5A 39 31` = ASCII `LZ91`

這是本節最重要的一條線索。`LZ91` 是 **LZEXE 0.91** 壓縮執行檔的識別標記，
位於 EXE 標頭 offset 0x1C（S24，shikadi ModdingWiki）。S04 的說明是：
`DATA5.GRP` 的這四個 byte 被改成 `20 20 20 20`（四個空白），**填回 `LZ91` 之後就能解壓**。

推得的結論（**推論，未親自驗證**）：

1. `DATA5.GRP` **不是資料檔，而是一個 LZEXE 壓縮過的 DOS 執行檔／overlay**。
2. 保護手法是把 LZEXE 的識別標記塗掉，讓 `UNLZEXE` 之類的標準工具認不出來。
3. 副檔名 `.GRP` 在這套遊戲裡**不代表統一的容器格式**——`DATA5.GRP` 與
   `DATA0~4.GRP` 很可能是完全不同的東西。這一點對解包工作的影響很大：
   不要假設六個 `DATA*.GRP` 同構。

`ASV.EXE` 那一段的「用 UNP 解壓二次」也指向同一類手法：UNP 是通用的 DOS 執行檔脫殼器，
「二次」表示外層套了兩層壓縮／加殼。

### 3.2 保護方式的描述

- S04：磁片加密碼（`保護：磁片＋密碼`）。
- S01／S03：介面採用「當時先進的語音系統」，保護方式為磁片加密。
- S07：正版需要用第一塊 5.25 吋磁片當作遊戲碟，該片防拷；第一片壞掉整套遊戲就報廢。
- 加強版 README（專案內檔案）：「密碼只須輸入一次」——表示原版每次啟動都要輸入密碼。

密碼多半是查手冊式的驗證（manual lookup），但**沒有任何來源說明密碼的內容或查詢方式**。

## 4. `.GRP` / `.IDX` / `.NAM` 三件套：沒有現成資料

專案內兩份 bundle 都有 `DATA0`～`DATA5` 各自的 `.GRP`／`.IDX`／`.NAM`。
針對這組容器，**網路上找不到任何分析**。

### 4.1 類比先例（不同遊戲，不可直接套用）

智冠 1996 年的《金庸群俠傳》使用 `.grp` + `.idx` 配對，其格式有公開研究（S18，CSDN）：

- `.idx` 每 4 byte 一個項目，記錄對應資源在 `.grp` 中的 **end offset**；
  該值同時是下一筆資源的 start offset。
- `.grp` 內每張圖：寬、高、X 偏移、Y 偏移各 2 byte，之後是逐行的 RLE 編碼像素；
  每行記錄「透明像素數」與「非透明像素數」，後接調色盤索引。
- 調色盤獨立放在 `Mmap.col`，256 色，每色 3 byte，數值為實際 RGB 除以 4
  （即 6-bit VGA DAC 值）。
- 該研究**完全沒有提到 `.nam`**。

**這是另一款遊戲、晚五年、不同引擎。** 兩者的共同點只有「智冠出品」與副檔名相同，
這連弱證據都算不上。用途僅限於：如果本作的 `.IDX` 剛好也是 4-byte end-offset 陣列，
那就少走一段路；如果不是，這份資料一點用都沒有。

### 4.2 `.NAM` 的線索：從檔案大小推

專案內兩版的檔案大小（`ls` 讀取，非網路資料）：

| 檔案 | `.IDX` | `.NAM` | `.NAM` ÷ `.IDX` |
|---|---|---|---|
| DATA0 | 2,418 | 688 | — |
| DATA1 | 868 | 3,472 | 4.0 |
| DATA2 | 2,024 | 8,096 | 4.0 |
| DATA3 | 1,688 | 6,752 | 4.0 |
| DATA4 | 172 | 688 | 4.0 |
| DATA5 | 260 | 1,040 | 4.0 |

`DATA1`～`DATA5` 的 `.NAM` 剛好是 `.IDX` 的四倍。`DATA0` 例外（2,418 vs 688，
比值 0.28）——而 2,418 不是 4 的倍數，這一項在整組裡本來就異常。

**推測**（未驗證）：`.IDX` 每項若干 byte、`.NAM` 每項為其四倍（例如 `.IDX` 每項 2 byte
的 offset、`.NAM` 每項 8 byte 的名稱），或 `.IDX` 每項 4 byte、`.NAM` 每項 16 byte。
`DATA0` 需要另外處理。**這是要用位元組驗證的第一個假設，不是結論。**

### 4.3 版本間的檔案差異（專案內觀察，非網路資料）

- `DATA1/2/3/4.GRP` 兩版位元組長度相同；`DATA0.GRP` 與 `DATA5.GRP` 不同。
  這與 README 說「加強版就是換掉 `DATA5.GRP`」大致相符，但 `DATA0.GRP` 也變了
  （原版 42,488 B，加強版 87,696 B），README 沒提。
- 原版目錄有 `10.GRP`、`20.GRP`、`10.BAT`、`20.BAT`、`D5.GRP`、`PLAY.BAT`、`PARTNSAV.FIL`；
  加強版目錄沒有這些，但多了 `NAME001~006.SHA`、`SV.COM`、`SV.PIF`、`ASV.PIF`、
  `CHKLIST.CPS`、一個 0 byte 的 `弧.TXT`。
- `10.BAT` 的內容是 `DEL DATA5.GRP` + `COPY 10.GRP DATA5.GRP`；`20.BAT` 同理換成 `20.GRP`。
  且 `10.GRP` 與該目錄的 `DATA5.GRP` **MD5 完全相同**。
  **推測**：`10`／`20` 是兩種預設，玩家用 BAT 切換 `DATA5.GRP`；名稱可能對應機器時脈
  （10 MHz／20 MHz），這與 README 第 4 條「語音功能可調整，一般 16MHz 機種約在 100」
  以及 S04「電腦速度太快會當機」相呼應。`D5.GRP` 則像是原始 `DATA5.GRP` 的備份
  （145,377 B，比 `DATA5.GRP` 少 1 byte，內容不同）。**全部是假設待驗。**
- 加強版的 `NAME001~006.SHA` 六個檔案，編號正好對應六個時期／六個存檔槽。
  `NAME001.SHA` 特別大（100,347 B），其餘五個約 7.3～7.6 KB。
  `.SHA` 的副檔名不明；**推測**與自建君主的手繪姓名點陣有關（S04 提到新君主姓名
  必須用繪圖方式製作，且可「讀取現有的字」）。**假設待驗。**

## 5. 執行環境（用得上的實務資訊）

| 項目 | 內容 | 來源 |
|---|---|---|
| 速度敏感 | 使用喇叭發聲時電腦速度不可太快，否則會當機。不是每次都當，多試幾次；只要通過喇叭發聲處理（即玩家的動作），後面遊戲過程中便不會再當 | S04 |

## 7. 建議的下一步（依成本／回報排序）

1. **直接跳到 `DATA2.GRP` 的 offset 818,235 讀 5 byte**。若是一個兩字 Big5 郡名加 NULL，
   S04 的整張位址表與三個結構版面就一次全部可用，而且郡名表也同時到手
   （往後每 176 byte 讀一次，共 42 次）。一次讀取就能否證或確立整套假設，
   是投報率最高的一步。
2. **驗證 `DATA5.GRP` 是不是 LZEXE**。把 offset 0x1C 的四個 byte 讀出來看是不是
   `20 20 20 20`，填回 `4C 5A 39 31` 後餵給 `unlzexe`。這是一次性、幾分鐘的檢查，
   而結果會決定 `.GRP` 要不要當成統一容器處理。
3. **驗證 `.IDX` 是不是 offset 陣列**。`.IDX` 檔小（172～2,418 B），
   直接把它當 2-byte 或 4-byte little-endian 陣列印出來，看數列是否單調遞增、
   末項是否等於對應 `.GRP` 的檔案長度。同樣是幾分鐘、結果自我驗證的檢查。
4. **解開諸侯區 1326 byte 的謎**。第 1 步成功之後，諸侯區的起點也就確定了，
   直接看那 1326 byte 是 17 × 78 還是 18 × 72 + 30。
5. 上面四步都做完之前，**不要開始反組譯 `AA.EXE`／`ASV.EXE`**。
