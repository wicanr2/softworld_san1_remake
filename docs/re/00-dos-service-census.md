# DOS 服務普查（dosgolem probe，第一輪）

日期：2026-09-06
工具：`dosgolem` `cmd/probe`，工作副本 `~/cht/dosgolem-san` 分支 `san1-msc-oracle`
（基準 commit `967ac40`）

```sh
DOSGOLEM_ORIG=~/cht/softworld_san/org_game tools/go.sh run ./cmd/probe \
  -exe "/orig/<版本目錄>/<EXE>" -root "/orig/<版本目錄>" -steps 5000000 -log-calls
```

## 結果

兩版跑滿 5,000,000 道指令上限，程式還活著，**停在同一種狀態**。

| | 原版 `AA.EXE` | 加強版 `ASV.EXE` |
|---|---|---|
| 停止時 CS:IP | `06DD:21E5` | `06DD:21C4` |
| 視訊模式 | `03h`（文字）| `03h`（文字）|
| 開過的檔 | 0 | 0 |
| 主控台輸出 | 空 | 空 |
| `A0000` 非零像素 | 0 / 64000 | 0 / 64000 |
| 滑鼠輪詢 | 0 | 0 |

服務呼叫（`L0`，probe 直接計數）：

| int 21h AH | 意思 | 原版 | 加強版 |
|---|---|---|---|
| `08` | 無回顯字元輸入 | 356,873 | 354,131 |
| `35` | 取中斷向量 | 12 | 12 |
| `25` | 設中斷向量 | 11 | 11 |
| `44` | IOCTL | 5 | 5 |
| `30` | 取 DOS 版本 | 2 | 2 |
| `4A` | 調整記憶體區塊 | 2 | 2 |
| `48` | 配置記憶體 | 1 | 1 |

## 讀出來的東西

**兩版的啟動輪廓逐項相同**（`L0`，`[both]`）。`AH=08` 以外六種服務的呼叫次數
完全一致，停止位址只差 `0x21`。這支持「兩版共用同一份 Microsoft C 6.0 CRT
與同一套啟動流程」，與 `CONTEXT.md` F1 一致。

`AH=35`／`25`（取／設中斷向量）各十來次是 MSC CRT 的標準開場——
接管除以零、Ctrl-Break、critical error 之類的向量。`AH=30`／`4A`／`48`
同樣是 CRT 的記憶體整理。**這一段還沒進遊戲碼。**

## 待辦：`int 21h AH=08` 未實作

`AH=08` 佔了全部呼叫的 99.99%，而 dosgolem 目前沒實作它，回 `AL=FF`。
真實 DOS 的 `AH=08` 是**阻塞式**讀取——呼叫一次就等在那裡直到有按鍵；
dosgolem 立刻返回，於是程式在同一個迴圈裡空轉三十幾萬次。

所以目前的「跑滿上限、程式還活著」**不是跑不動，是卡在等鍵盤**。
在 `AH=08` 補上之前，兩支執行檔都走不到開檔與繪圖，
`A0000` 全零與「開過的檔 0」這兩個數字**不能拿來下任何結論**。

下一步（`dosgolem-san` 分支）：

1. 在 `internal/dos` 實作 `AH=08`：從鍵盤佇列取字元，佇列空時的行為要與
   真實 DOS 一致（阻塞／讓出，而不是回 `FF` 繼續跑）。
2. 用 probe 的 `-keys` 餵鍵，重跑，看它走到哪裡。
3. 走到開檔之後，`開過的檔` 那一欄就會開始回答「三件套是怎麼被讀的」——
   這是 `CONTEXT.md` §3.1 那個 `.IDX` 矛盾最直接的觀測點。

## 這一輪沒有回答的

- 兩支執行檔用不用得到 8086 以外的指令（`rich2` 那邊是 80186 的 `PUSH imm`）。
  probe 沒報未知指令，但**沒跑到遊戲碼**，所以這是假零，不是結論。
- 圖形模式、檔案存取、音效（PC 喇叭）一概還沒觀測到，理由同上。
