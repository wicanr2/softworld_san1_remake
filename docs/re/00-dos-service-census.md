# DOS 服務普查（dosgolem probe，第一輪）

日期：2026-09-06
工具：`dosgolem` `cmd/probe`，工作副本 `~/cht/dosgolem-san` 分支 `san1-msc-oracle`
（基準 commit `967ac40`）

```sh
DOSGOLEM_ORIG=~/cht/softworld_san/org_game tools/go.sh run ./cmd/probe \
  -exe "/orig/<版本目錄>/<EXE>" -root "/orig/<版本目錄>" -steps 5000000 -log-calls
```

## 結果

兩版跑滿 5,000,000 道指令上限，程式還活著，**停在同一種狀態**。

| | 原版 `AA.EXE` | 加強版 `ASV.EXE` |
|---|---|---|
| 停止時 CS:IP | `06DD:21E5` | `06DD:21C4` |
| 視訊模式 | `03h`（文字）| `03h`（文字）|
| 開過的檔 | 0 | 0 |
| 主控台輸出 | 空 | 空 |
| `A0000` 非零像素 | 0 / 64000 | 0 / 64000 |
| 滑鼠輪詢 | 0 | 0 |

服務呼叫（`L0`，probe 直接計數）：

| int 21h AH | 意思 | 原版 | 加強版 |
|---|---|---|---|
| `08` | 無回顯字元輸入 | 356,873 | 354,131 |
| `35` | 取中斷向量 | 12 | 12 |
| `25` | 設中斷向量 | 11 | 11 |
| `44` | IOCTL | 5 | 5 |
| `30` | 取 DOS 版本 | 2 | 2 |
| `4A` | 調整記憶體區塊 | 2 | 2 |
| `48` | 配置記憶體 | 1 | 1 |

## 讀出來的東西

**兩版的啟動輪廓逐項相同**（`L0`，`[both]`）。`AH=08` 以外六種服務的呼叫次數
完全一致，停止位址只差 `0x21`。這支持「兩版共用同一份 Microsoft C 6.0 CRT
與同一套啟動流程」，與 `CONTEXT.md` F1 一致。

`AH=35`／`25`（取／設中斷向量）各十來次是 MSC CRT 的標準開場——
接管除以零、Ctrl-Break、critical error 之類的向量。`AH=30`／`4A`／`48`
同樣是 CRT 的記憶體整理。**這一段還沒進遊戲碼。**

## 待辦：`int 21h AH=08` 未實作

`AH=08` 佔了全部呼叫的 99.99%，而 dosgolem 目前沒實作它，回 `AL=FF`。
真實 DOS 的 `AH=08` 是**阻塞式**讀取——呼叫一次就等在那裡直到有按鍵；
dosgolem 立刻返回，於是程式在同一個迴圈裡空轉三十幾萬次。

所以目前的「跑滿上限、程式還活著」**不是跑不動，是卡在等鍵盤**。
在 `AH=08` 補上之前，兩支執行檔都走不到開檔與繪圖，
`A0000` 全零與「開過的檔 0」這兩個數字**不能拿來下任何結論**。

下一步（`dosgolem-san` 分支）：

1. 在 `internal/dos` 實作 `AH=08`：從鍵盤佇列取字元，佇列空時的行為要與
   真實 DOS 一致（阻塞／讓出，而不是回 `FF` 繼續跑）。
2. 用 probe 的 `-keys` 餵鍵，重跑，看它走到哪裡。
3. 走到開檔之後，`開過的檔` 那一欄就會開始回答「三件套是怎麼被讀的」——
   這是 `CONTEXT.md` §3.1 那個 `.IDX` 矛盾最直接的觀測點。

## 這一輪沒有回答的

- 兩支執行檔用不用得到 8086 以外的指令（`rich2` 那邊是 80186 的 `PUSH imm`）。
  probe 沒報未知指令，但**沒跑到遊戲碼**，所以這是假零，不是結論。
- 圖形模式、檔案存取、音效（PC 喇叭）一概還沒觀測到，理由同上。

## 第二輪：實作 `AH=08` 之後（同日）

在 `dosgolem-san` 補了 `int 21h AH=01h`／`07h`／`08h`（`conIn`）與 `AH=0Bh`，
並加了 `DOS.KeyWaits` 計數。probe 的「沒實作的服務」歸零。

**行為沒有改變**：兩版仍然跑滿上限、零開檔、零繪圖，`KeyWaits` 等於原本的
`AH=08` 呼叫次數。餵 `-keys`（Enter ×8、空白、`y` 三種都試過）也沒有前進，
`AH=08` 的次數三種按鍵下**完全相同**（571,159）——餵進去的鍵被瞬間吃掉，
迴圈次數由「佇列空」那一支主導。

### 迴圈長什麼樣（`-trace`，`L0`）

十四道指令一圈，跨兩個段：

```
24D9:002D → 06DD:21C2   AX=0000
            06DD:21C4   AX=0000
            06DD:21C7   AX=FFFF   ← AX 先變成 FFFF
            06DD:21C9   AX=FFFF
            06DD:21D3   AX=FFFF
            06DD:21D9   AX=FFFF
            06DD:21E4   AX=FFFF
            06DD:21E5   AX=08FF   ← AH←08，AL 還是殘留的 FF
            06DD:21E7   AX=0800   ← int 21h 發生，conIn 回 AL=0
            06DD:21E9   AX=0000   ← AH 被清掉，取成一個字元值
24D9:0032 → 24D9:0035 → 24D9:0037 → 24D9:002D（回到開頭）
```

`06DD:21C2` 起是 getch 的包裝常式，`24D9:002D`–`0037` 是呼叫端的迴圈。

### 這個空轉是我們造成的，不是遊戲的行為

真 DOS 的 `AH=08` **阻塞**：呼叫一次就停在那裡，一道指令都不走，直到有人按鍵。
步進式執行器停不下來，只能返回；於是 `while (getch() != X);` 這種寫法
在 dosgolem 底下變成緊迴圈。

所以「跑滿五百萬道指令」**不是遊戲卡住，是模型不對**。目前的
「零開檔」「`A0000` 全零」「`B8000` 全零」全部是這個模型缺陷的下游，
**一個都不能當成對遊戲的觀測**。

### 下一步：`AH=08` 要能真的停下來

`conIn` 現在回 `AL=0` 讓程式繼續跑，是三個爛選項裡最不會說謊的一個
（不動 `AX` ＝ 餵垃圾當按鍵；餵 `StdinFill` ＝ 假裝有人按了）。
但正確的模型是**停機**：佇列空時讓執行迴圈停下來並回報「在等鍵盤」，
由呼叫端餵鍵再繼續——也就是 `rich2` 那邊 `RunUntil(PasswordScreen)` 的形狀。

這是 dosgolem 的設計決定，不是這個遊戲專屬的，要走 `docs/spec/`。
在它做完之前，這一款走不到開檔與繪圖。

### 它在等什麼鍵——見第三輪

（第二輪當時猜這個迴圈可能是密碼輸入。第三輪量出來不是，
推翻紀錄在 `CONTEXT.md` §4 R2。）

## 第三輪：阻塞模型上線之後（同日）

dosgolem 補上阻塞語意（`dosgolem/docs/spec/008`，READY）：佇列空時
`cpu.Rewind()` 把 `CS:IP` 退回那道 `INT`，程式一道指令都不往前走。

### 阻塞時真的不動了（`L0`）

`-trace` 顯示 `CS:IP` 與所有暫存器釘在 `06DD:21E5`／`AX=0820` 完全不變。
第二輪那個十四道指令的緊迴圈消失了。

⚠ **`AH=08` 的呼叫次數反而上升**（3,000,000 步裡 2,996,222 次），
因為那道 `INT` 每一步都重跑。拿呼叫次數當「有沒有改善」的指標會得到
相反的結論——**要看的是程式有沒有往前走**。

### 它在等的是選單，不是密碼（`L0`）

把 ESC、Tab、CR 加上全部可列印 ASCII（98 個鍵）一次餵進去，
只有 **`1` 與 `2`** 被接受並回顯，其餘 96 個被吃掉沒有反應。
輸入 `2492` 只回顯兩個 `2`（那串裡剛好有兩個 `2`），`0000` 一個都沒回顯。

回顯走 `int 21h AH=06`（直接主控台輸出），總共三次。
**所以是連續三個「1 或 2」的提示**，不是四位數密碼欄位。

這也解釋了 `B8000` 為什麼全零：這一段走的是 DOS 主控台 I/O，
不是視訊記憶體。

### 過了這一關（`L0`）

餵八個 `1`：`CS:IP` 離開 `06DD:21xx` 走到 `06DD:1685`，
之後跑了 **約 790 萬道指令**才再次阻塞（基準是 53,778 道）。
只餵三個 `1` 不夠——還有第四個提示，而且它**不回顯**。

### 那三個提示大概是什麼（`L3`，未驗）

- `DATA1.NAM` 裡有 `EGAFILL.PAL` 與 `HERCFILL.PAL`（`docs/formats/01`），
  所以其中一題**可能**是 EGA／Hercules 顯示卡選擇。
- `AA.EXE` 的子系統名表裡有 `AdLib`／`Music`／`Sound`，
  所以**可能**有一題是音效裝置。
- `README.DOC` 提到語音速度可調（1–30000，16MHz 機種約 100），
  那 790 萬道指令**可能**是速度校正迴圈——這種迴圈正好會燒掉大量指令
  而沒有任何可觀測的輸出。

**三條都是從命名與旁證推的，一條都沒驗。** 要確認就去反組譯
`06DD:21C2` 那支包裝常式的呼叫端，看提示字串從哪裡來。

### 還是沒有的

零開檔、零視訊寫入、視訊模式仍是 `03h`。790 萬道指令做了什麼還不知道。
